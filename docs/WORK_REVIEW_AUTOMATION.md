# MT-AUTO-001: powiadomienie o zakończonej próbie CI

Workflow [`PR Review CI Completion`](../.github/workflows/review-ci-completed.yml) reaguje na zakończenie workflow `CI` dla PR. Działa z domyślnej gałęzi `main`, używa wyłącznie wbudowanego `GITHUB_TOKEN` i kodu pobranego z `main`. Nie pobiera ani nie wykonuje kodu z gałęzi PR. Potrzebuje `contents: read` do checkout i wyszukania PR dla commita, `actions: read` do ponownego sprawdzenia przebiegu oraz `pull-requests: write` do własnego komentarza. Nie używa sekretów, PAT, formalnego GitHub APPROVE, merge ani deploy.

Bot publikuje najwyżej jeden własny komentarz dla pary PR + pełny HEAD SHA. Znacznik ma postać `<!-- math-tutor-ci-gate:v1 pr=NUMER sha=SHA -->`. Ponowny ukończony przebieg CI dla tego samego SHA aktualizuje komentarz, a opóźnione zdarzenie starszej próby jest ignorowane. Komentarz podaje `CI_RUN_RESULT` dla konkretnego numeru run i próby jako **historycznie zaobserwowany fakt**. `CURRENT_CI` i `CURRENT_READINESS` pozostają niepotwierdzone; `CODE_REVIEW` nie jest oceniane przez ten workflow, `PHYSICAL_SAFARI` pozostaje `NOT_VERIFIED`, a `OWNER_APPROVAL` — `REQUIRED`.

GitHub nie oferuje atomowego odczytu stanu CI, HEAD PR i komentarzy Work. Rerun albo edycja recenzji mogą nastąpić podczas dowolnego odczytu. Dlatego notifier **nie łączy** tych danych w aktualną zieloną bramkę: nie interpretuje komentarzy Work i nigdy nie publikuje `CODE_REVIEW_PASS_AND_CI_GREEN`. Przed zapisem sprawdza HEAD ponownie, lecz nawet zmiana po tej kontroli nie zamienia historycznego wyniku próby CI w deklarację gotowości. Aktualne CI i raport Work trzeba odczytać osobno przed decyzją użytkownika.

## Konfiguracja zadań ChatGPT Work

1. **Recenzent**: zachowaj wyzwalacze `PR opened` i `PR synchronize`. Warunek: `eluyz/math-tutor-app`, otwarty PR do `main`; audytuj dokładny HEAD SHA, kod, matematykę, PL/EN, regresje i CI. Oznacz komentarz `<!-- math-tutor-work-review:v1 pr=NUMER sha=SHA -->` i opublikuj jednoznaczny status (`NEEDS_FIXES`, `PASS`, `READY_FOR_USER_APPROVAL` albo `WAITING_FOR_CI`). Jeśli raport `WAITING_FOR_CI` kończy audyt kodu bez blokad, dodaj osobną linię `<!-- math-tutor-work-audit:v1 blockers=none -->`. Nie dodawaj jej przy nieukończonym audycie lub znanym defekcie.
2. **Finalizator**, wyłącznie jeśli konto Work oferuje wyzwalacz **nowy komentarz PR**: ogranicz go do komentarzy w `eluyz/math-tutor-app` od `github-actions[bot]` (GitHub user ID `41898282`) z dokładnym znacznikiem `math-tutor-ci-gate:v1`. Dla ponowionej próby CI bot **edytuje** komentarz; automatyczny sygnał także po rerun wymaga więc wyzwalacza edycji komentarza, jeśli Work go oferuje, albo monitorowania harmonogramem. Komentarz bota jest sygnałem historycznego zakończenia próby, **nie aktualną zieloną bramką**. Przed publikacją sprawdź przez GitHub API, że PR jest nadal otwarty, baza to `main`, repozytorium HEAD jest to samo, SHA w znaczniku równa się bieżącemu `PR.head.sha`, a **najnowsza próba** workflow `CI` faktycznie zakończyła się podanym wynikiem. Odczytaj własny istniejący raport recenzji dla tego SHA. Opublikuj brakujący końcowy stan lub instrukcje naprawy; nie powtarzaj pełnego audytu bez nowych commitów, nie uznawaj sukcesu CI za `CODE_REVIEW_PASS` i nigdy nie ogłaszaj READY przy błędzie blokującym. Nie traktuj kolejnych komentarzy finalizatora jako nowego sygnału, aby uniknąć pętli.
3. Jeśli trigger komentarza PR nie jest dostępny, pozostaw samodzielne powiadomienie GitHub. Opcjonalny harmonogram Work może okresowo sprawdzać otwarte PR z raportem `WAITING_FOR_CI`, lecz musi weryfikować aktualny HEAD i najnowszą zakończoną próbę CI przed zmianą własnego statusu. Harmonogram nie jest skonfigurowany w tym PR.

Samo pojawienie się komentarza bota **nie dowodzi**, że Work uruchomił finalizator. Dostępność wyzwalacza Work: **NOT_CONFIRMED**. Nie mamy tutaj dostępu do konfiguracji event-trigger tego konta i nie należy przedstawiać instrukcji jako dokonanej zmiany w Work.

## Kontrolowany test po osobnej zgodzie na merge

GitHub uruchamia `workflow_run` tylko wtedy, gdy plik workflow znajduje się na gałęzi domyślnej. Dlatego PR z MT-AUTO-001 może przetestować logikę w izolowanych fixture/mockach i własne CI, ale **nie może potwierdzić działania wyzwalacza produkcyjnego**. Po zatwierdzonym scaleniu do `main` utwórz nowy mały testowy PR (nie PR #25), odczekaj na ukończenie jego `CI` i sprawdź:

1. Jedyny komentarz `math-tutor-ci-gate:v1` odpowiada numerowi PR, SHA i rzeczywistej konkluzji/linkowi konkretnej próby run; ponowna ukończona próba CI aktualizuje go bez duplikatu. Podczas trwającego rerun nie ma deklaracji bieżącego sukcesu.
2. Zakończenie `CI` po zmianie HEAD nie oznacza starszego SHA jako gotowego; push na `main` i PR z forka nie otrzymują powiadomienia.
3. Jeśli skonfigurowano wyzwalacz komentarza w Work, sprawdź w historii jego zadań, czy uruchomił się **od komentarza bota**, a następnie czy opublikował decyzję dla dokładnego SHA. Jeśli nie, oznacz tryb `NOT_CONFIRMED` i użyj samodzielnej bramki lub monitorowania harmonogramem.

Powiadomienie i recenzja nie zastępują osobnej zgody właściciela na merge ani fizycznego testu Safari. Testowego PR nie wolno scalać lub wdrażać automatycznie.
